# SmolVLA 主线与实验优先级：先证明完整协作，再深挖微机制

2026-09-30。本文取代旧计划的项目执行顺序，不覆盖历史实验结果。
本次只调整研究组织与审查门槛，没有新增硬件测量。

## 1. 收敛到一条工作主线

**工作主线：网络受限时，多视角 flow VLA 的端侧 NPU 与远端 GPU 如何协作，才能比优化全端和流式全云更早完成一个完整动作块？**

这是待验证的技术路线，不是已经成立的论文贡献。目标是 Technique paper；
暂不宣称提出了全新的问题。重点不是做一个泛用卸载调度器，而是找到一个
由 VLA 数据依赖和真实硬件成本共同决定、强控制仍未解决的执行障碍。

直白的痛点是：云端算得快，但必须等观测跨网；端侧不等网络，但当前完整策略
仍慢。把部分计算留在端侧，看似可以两边同时干，实际上也可能多传更大的
特征、多等一次汇合，最后比全端和全云都慢。**我们要研究的是怎样让两边的
工作真正抵掉等待，而不是仅让两个设备同时显示“忙”。**

已有发现提供了一个切入口：端侧的并行收益不是可以随意相加的。单相机
head 并行约快 32%，双相机相对整相机并发强控制仅快约 6%；再叠相机并发
不到 1%。因此不能用“卸走一半视觉工作，再加一个单相机加速比”预测协作。
这确认了收益不能简单外推；共享资源竞争是待定位的解释，尚未归因到计算、
DDR 或驱动。**没有证明最优配置反转，更没有证明端云协作一定赢**。

候选洞察只有一句：**端云分工可能改变端侧剩余工作的并行条件，执行位置、传输
表示和端侧执行方式应按完整观测的关键路径一起判断，而不能分别优化后相加。**
它还只是机制假设；若一个固定配置加普通卸载就解决问题，不能把这句话包装
成创新。后续实验必须同时回答“有无完整收益”和“普通办法为什么仍不够”。

范围固定为 `HuggingFaceVLA/smolvla_libero`、实际双视角、原动作专家和十步
依赖 flow。当前设备是 RK3588 与近端 RTX 服务器，可通过受控链路研究网络
限制；不是已经验证的三层端边云或公网云部署。不用 freshness、运动物体、
Agent、大小脑或长程规划作尚无证据的核心动机。

## 2. 用 V 与 A 的依赖约束组织系统

```text
同一观测的相机 0 → 完整视觉编码 ─┐
                               ├→ 汇合全部视角 → 多模态 Prefill
同一观测的相机 1 → 完整视觉编码 ─┘                 ↓
                                         本观测固定 conditioning
                                                  ↓
                                原十步 flow：velocity → FP32 Euler
                                                  ↓
                                         完整动作块返回端侧
```

- **V 提供观测内并行：** 两个视觉分支在汇合前独立，适合重叠本地计算、图像上传
  与远端计算。上传顺序、共享链路和两路完成时间都影响汇合。
- **A 约束协作粒度：** conditioning 在本次十步中不变，latent 却逐步依赖。
  当前优先让 Prefill 和完整动作循环在同一端完成，不在十步之间反复跨网。
  CPU FP32 Euler 留在执行该循环的主机，不能在 NPU 上偷偷改数值协议。
- **异构角色由测量决定：** CPU 做实际编解码、原生接口与原有辅助计算；NPU
  承担端侧主网络；GPU 承担远端完整分支或后半程。不是预设 CPU softmax
  更快，也不是为了使用所有设备而制造拆分。

独立分支先完成不代表可以单视角直接执行原多模态 Prefill；不能漏掉另一视角、
用旧帧替换，或把自回归动作 token 的投机验证直接套到 flow latent 上。

先比较下面的有限计划族，不搜索任意逐层切点，不先建设通用 runtime：

| 执行计划 | 视觉分工与汇合位置 | Prefill / 完整十步动作 | 必须支付的成本 |
|---|---|---|---|
| 优化全端 | 两路端侧 NPU，现有最快合法完整配置 | 端侧 | 真实预处理、原生接口及全部策略工作 |
| 流式全云 | 两路无损图像上传；远端收到一路即可开始该路编码 | 远端 | 编码、共享上行、远端计算、动作返回；允许上传/计算重叠 |
| 一端一云、端侧汇合 | 一路 NPU，一路 GPU；远端 connector 返回端侧 | 端侧 | 一路图像上行、云特征下行、汇合等待及端侧完整后半程 |
| 一端一云、远端汇合 | 一路 NPU 特征上传，另一路图像上传后 GPU 编码 | 远端 | 两种 payload 共用上行、编码/打包、汇合等待及远端完整后半程 |
| 全端视觉、远端后半程 | 两路 NPU 特征上传、远端汇合 | 远端 | 两路特征上传及完整后半程；优先做支配性检查，不默认值得实现 |

分支协作应交换相机分工验证，不假定两幅图的编码字节完全相同。远端生成的
FP32 特征必须按其原精度无损传送，不能套用端侧原生 FP16 payload 字节。
Prefill K/V 大张量跨网、动作循环逐步迁移和重复整模型 hedge 暂不加入主计划族。

## 4. 新执行顺序与退出条件

**依赖关系：P0 → P1 → P2 → P3。** P0/P1 决定是否值得继续这条主线；局部
探针不是另一条同等优先的主线，也不是本路线失败后的自动备用故事。
以下是工作量预算，不是已完成状态或承诺日程。

| 优先级 / 预算 | 动机与目的 | 最小实验及预期成果 | 风险与决策门槛 |
|---|---|---|---|
| **P0：匹配的完整服务与依赖账本；1–2 个工作日** | 当前本地证据充分，匹配远端和完整网络请求证据缺失；不补齐就无法决定研究价值 | 复用三帧 manifest/权重/噪声，补 GPU 单/双视觉、Prefill、十步 flow 及完整策略；用请求端统一起止边界测全端/流式全云；输出服务表和完整时间线 | 不重跑已完成的十套本地矩阵。不混用旧云闭环数；计入预处理、codec、传输与返回；异步 GPU 计时必须等待真实完成 |
| **P1：完整协作可行域与支配性检查；1–2 个工作日** | 先确认协作值得做，而不是先优化某个很小的接口 | 用 P0 服务和真实 payload 建乐观下界及成本模型，比较五类合法计划与两端强控制；筛出有潜力区域后做真实链路复验；输出可行域图、损益表及反例 | 模型预测标为预测，不冒充实测。若给协作免费重叠/零额外交接仍无胜区，就停止该单请求路线；若只赢弱全云或事后挑的网络，也不通过 |
| **P2：关键路径上的最小机制；首轮 2–3 个工作日** | 有协作胜区不等于有创新；确定普通静态分工和独立调优留下了什么 | 固定 P1 的一个重要边界，对照联合配置、只选位置、只调本地和最佳静态计划；同工作量做有/无 overlap 消融，核验关键路径如何改变 | 若普通静态分工吸收收益，保留部署结果，不声称新调度机制。没有重要剩余障碍，不扩 runtime；只跟进完整时间线上真正限制收益的微机制 |
| **P3：成立后的完整系统验证；通过 P2 后细化预算** | 将合法小机制转成可信系统结果，而非固定形状小技巧 | 接完整策略，扩大真实 episode/指令覆盖，测实际网络轨迹、闭环质量、尾延迟、持续热状态、隔离内存和能耗；输出完整收益及失败范围 | 三帧数值相似不是质量证明；少量重复不够稳定 P95。全部视角、heads/tokens、动作数、十步依赖和精度配置必须保留 |

### P0 的统一协议

主指标为**同一观测、状态和指令已在端侧可用，到完整动作块在端侧可消费**的
墙钟时间。另保留模型内分项，解释与约 2.08 s 离线起点的关系，不把两个
计时范围直接算加速比。模型初始化独立报告；暖连接与冷连接分开。

同一次请求记录图像准备/编码、上传、分支计算、汇合、Prefill、动作循环与返回。
正式总时延在请求端测；多机阶段若未校准时钟，报告各端持续时间与因果事件，
不拼接伪精确的跨机时间轴。并发时使用实测 makespan，不能相加各阶段中位数。
状态、指令与噪声/请求元数据的传输也计入，不只统计相机 payload。

固定 checkpoint revision、全部输入、初始噪声数组和目标精度配置。纯端/纯云
各有后端 anchor；混合计划另建**相同放置、串行执行**的 anchor，验证传输、
并行和接口改写没有增加数值变化。新增本地图改写仍须通过原融合逐位门槛。
跨 CPU/NPU/GPU 原本存在的浮点差异不能称为逐位等价，仍需完整动作及闭环
质量验证；若超出既定无损协议，排除该实现，不靠放宽阈值救性能。

视觉 head 分图目前不是完整策略合格基线：先保留融合策略控制，并单独完成
其动作轨迹/质量审计；未通过原数值门槛前，只能作为潜在更强对照或诊断，
不能作为论文方案的合法加速。不为证明协作而刻意忽略这个更强替代。

### P1 的网络与公平性

先冻结分析网格：上行 0.5/1/2/5/10/20/50 Mbps，下行 2/10/50 Mbps，RTT
5/20/50/100 ms。网格覆盖受限到相对充足链路，不是“这些条件已经在现场
出现”的声明。先在整个网格跑成本分析；真实复验须包含预测交界两侧、
明显全端占优区和明显全云占优区。再用测得的链路轨迹验证，实测吞吐/RTT
与配置值分别报告；不得只保留协作获胜的片段。

全云必须允许逐相机上传与视觉编码重叠；两视角共用链路预算，无损 codec
给双方同等选择机会，CPU 编码与 NPU 执行并发的争用须计入。先测空闲 GPU，
不假设云端有任意大的排队。若后续研究负载，使用真实可复现队列，并同时
给全云批处理/并发服务强控制。多机器人吞吐/GPU 成本是另一个目标，不能
在单请求加速失败后悄悄换指标救主线。

先找成本模型中的支配关系，再决定实现预算。例如：若图像比特征更小、GPU
编码更快且无排队，那么“端侧编码后把特征交给云端”可能被流式全云直接
支配。反方向在端侧汇合虽少上传一路，却多付一次特征下行并保留端侧约
0.99 s 后半程。这些是**待 P0 验证前提的反证推演**，不是已经测得的否定结论。

### P2 怎样决定深挖什么

先做“放置 × 本地配置 × 传输/计算是否重叠”的小型交叉实验。逐条件离线
最佳计划是性能上界参照，不是无需预测的可部署调度器。与最佳固定计划和
普通按链路选择全端/全云都比较：前者可能足够，后者可能吸收所谓联合收益。
只有观测到重要残差，才提出对应机制；不预先凑三项创新。

微机制只有三个入口：减少真实关键路径上的表示/交接成本；让合法独立工作
抵掉传输等待；修复关键阶段的执行几何。它们是同一个主线的支撑实验，
不是必须全实现的模块。无真实净收益或仅恢复人为劣化接口，就停止该版本。

**当前局部事项降级：** 视觉阶段几何保留为限时支撑，最多先用 1–2 个工作日
定位原融合数值边界；不扩十二层扫点、不当作项目第一任务。原生位桥接保留
代码和证据，不铺全部动作层。CPU softmax/tile、prefix/首步交错、flow 迁移、
hedge 和严格投机兼容性均暂停，除非 P0/P1 时间线给出必要且重要的理由。

## 5. 自审：先用强反例拆自己的故事

| 审查问题 | 当前答案 / 修正 | 严重性 |
|---|---|---|
| 协作真的比两端快吗？ | **未证明。** 特征更大与端侧后半程可能让全部混合计划失败；P0/P1 是立题前置，不是论文补充实验 | MAJOR，可实测判定；若乐观下界也被支配则该路线 CRITICAL |
| 联合优化不就是普通动态卸载吗？ | **目前差异不够。** 必须找到普通放置/静态调优未解决的原因和可重复机制；不是用三个名词拼新系统 | MAJOR；若强控制吸收所提机制，则该版本 CRITICAL |
| 是不是仍只围着几个毫秒钻？ | 局部几何与位桥接改为支撑项，先完整关键路径、后机制；预算由可归因的完整收益决定 | 执行顺序已修正，重要性证据仍未闭合 |
| 与 VLA 有什么关系？ | 多视角独立后汇合、固定条件服务依赖 flow；必须在 V 与 A 完整链上验证，而非只报 Transformer GEMM | 结构已明确，结构性增益待消融 |
| 无损与质量是不是偷换？ | 传输逐位、同后端图改写逐位、跨后端差异和任务质量分别报告；几何失败不能计为加速 | 协议已明确，合法实现与闭环待验证 |
| 网络场景是不是为了让方法赢而挑的？ | 网格先冻结，包含两端各自获胜区；实际轨迹与预测分开，队列不是免费假设 | 协议已明确，实测代表性待补 |

**审查结论：有条件继续，但本阶段投入限定为先完成 P0/P1；尚不值得按 CCF-A 论文规模
投入完整调度器。** 本轮获得的是清晰的研究对象与可证伪顺序，不是给局部
结果换一个更大的标题。若主线被反证，归档理由，再重新立题，不自动接续
另一个小探针当新故事。
